## 审计边界

本轮只检查 JSON 交接：ASECLI 的候选/名称槽位绑定、资源证明、公开 report、发布入口，以及 SGCLI 的文件加载、Schema、certify、v3→v2 预处理和创建调用链。以本轮当前工作树为准，包含上一轮修复，不修改业务实现。

方法为只读源码、相关 pytest、临时目录中的测试夹具和内存 mock。未改生产 spec/report/receipt、源 Shader、材质、URP 包，未连接或启动 Editor。本报告中的 spec 变体仅是负向测试，不是通过手工改写生产转换规格绕过转换流程。

两端 `sgcli.native.v3` Schema SHA 都为 `bb16ce3f61e0772c51bcbfe89cd010ee426db12c59a6e84afad34fd512b41b82`。本轮没有发现 Schema 快照不同步。不能将下面的故障边界推断为现有 WaveNoise 产物已经遭到替换或贴图已错。

## 威胁与失败模型

- 资产：实际交给 Editor 的图、属性/资源内容、report/receipt 的可信含义。
- 生产者可能出现映射错误、过时报告或重新发布文件；消费者需要检测可证明的矛盾。
- 文件可以被同一用户的其他任务/程序在两次读取之间替换。
- 不同项目可能保留同一个 Unity GUID，但贴图内容和平台导入设置已分叉。
- 同一种 SG 节点可以通过 CLI 别名或合法原生完整类型名表达。
- SHA 是内容绑定，不是来源签名；攻击者能同时任意改写全部证据时，不能靠裸 SHA 证明真实性。本审计不将这一固有限制本身报为鉴权漏洞。
- 最贵失败是创建/认证成功但消费了不同图、不同纹理或执行了不同输出公式。

## Findings 详情

### [P1] AA-JSON-001 — 用同一 spec 快照完成加载与认证

位置：`/Users/long/GitHub/SGCLI/src/sgcli/native/commands.py:172`、`:188`；`native/conversion_gate.py:28`。

`_load_request` 先调用 `spec.load_for_command` 得到 request A 和 SHA A，再通过 `_conversion_certification` 调用 `certify`，后者重新读取 spec。认证没有接收第一次读入的 bytes/SHA，也不返回第二次 spec SHA 供调用方比较。创建后 `_result_metadata` 可同时输出 SHA A 和认证 B 的 true。`sg contract` 也存在相同双读。

触发：第一次读取 A 后，文件被替换为有有效 report/receipt 的 B。无需碰改 B 的有效证据。创建逻辑继续使用 A 的内存对象，却附上 B 的认证。

已验证：复用 `tests/native/test_conversion_gate.py::_bundle`；mock `Path.read_bytes`，仅该 spec 首次返回改名为 `UNVERIFIED_A` 的合法 bytes A，第二次返回原 bytes B。调用真实 `commands._load_request(args, 'create')`，结果：

```text
loaded_name = UNVERIFIED_A
loaded_sha = 0745fa6146ae9e7f356182db8d4987ef45feb4588816503ea27e4d8d798073c2
certified_spec_sha = aed4618d3a398a3230dc1d684412d744700867c59ecd5b994e960ef984baf55f
semantic_certified = true
spec_reads = 2
```

未实际竞争调度或创建 Unity 资产；此 mock 确定性重现文件变化时的调用链行为。A 不必只改名称，也可以是另一份可创建的计算图。

修复：读取一次不可变快照，Schema、认证和创建均用此快照；或者将初读 SHA 作为认证强制前置条件并比较。不要只在最后再读第三次文件。

### [P1] AA-JSON-002 — 语义门禁统一使用规范节点类型

位置：`/Users/long/GitHub/SGCLI/src/sgcli/native/surface_guard.py:39`、`:106`；`native/spec_v2.py:76` 的 bind_node。

输入 `type="custom-function"` 会进入重复调制和未知函数检查，但合法完整类型 `UnityEditor.ShaderGraph.CustomFunctionNode` 不满足这两个字符串判断。Schema 允许原生类型名，bind_node 也会从 catalog 绑定此类型，并保留原输入字符串。

已验证两个层面：

1. 完整类型名配 `Out = lerp(float3(1,1,1), C, A);`，对隔离夹具更新 SHA 绑定后，真实 `_load_request`/`certify` 返回 `semantic_certified=true`。
2. 使用测试中已声明的合法 CustomFunctionNode/Vector1Node catalog 形状，完整类型名经过 `validate_native_spec` 和 `spec_v3.prepare` 均被接受；将同一节点仅改回别名 `custom-function` 后立即报 SEM-BLEND-001。

反例条件：Transparent/Multiply；函数输入 C=(0.2,0.2,0.2)、A=0.5；另一个 `float` 节点 0.5 接 Surface Alpha。图中输出为 0.6，URP 再调制成为 0.8。这是公式推导，不是本轮 GPU 测量。

上一轮恢复了 fail_unproved，但其外层仍只检查别名，因此该问题仍存在。当前 ASECLI 通常输出别名；风险位于消费者公开 JSON 接口，并不证明当前 WaveNoise 精确模式有重复调制。

修复：在可信目录绑定后统一规范类型，或者在认证和 prepare 两处共用能识别别名/原生名的类型分类器；语义检查不能取决于同一节点的拼写形式。

### [P1] AA-JSON-003 — 资源证明包含内容与有效导入设置

位置：`/Users/long/GitHub/ASECLI/src/asecli/sg_export/sources.py:143`、`:210`；`sg_export/conversion_report.py` 的 `_resources_verified`；`sg_export/report_semantics.py` 的 resources 证据。

`texture_dependency` 比较有限的导入整数，但不读取/比较源与目标纹理内容。`_texture_importer` 按正则取每个 key 的第一个值；平台覆盖、maxTextureSize 等不参与对比。随后 `_resources_verified` 将 `verified_importer` 当作资源已证明。

已验证临时源/目标 Unity 项目：各有合法 1×1 PNG，源为红色、目标为蓝色；GUID 都为 `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`，14 个被读取的导入字段相同。Android 平台覆盖分别为 2048 和 32。实际调用 resolve_asset、texture_dependency 后得到 `status=verified_importer`，未报错。

```text
source PNG SHA = b1ff9c8ea3a780bad09b346c423d2d0e46815926879b18e841d928376a946640
target PNG SHA = fce481932ea5d07a91c7991c09fdadb4bf78f9b4cc8f927188384231f9d12679
status = verified_importer
```

证据限定：上述反例直接验证资源层；没有用这个夹具跑完整 ASE 图导出/Editor 导入。源代码可确认公开报告只看此 status，且不携带可由消费者复核的内容摘要。Android 最大尺寸对本例 1×1 PNG 不产生尺寸差，但不同大纹理/平台配置会产生实际行为差异；红蓝像素不同本身已足以否定资源等价。

修复：同格式资源至少比较内容 SHA，并把源/目标内容、meta 与目标平台有效 importer 状态写入独立机器证据，交接时复核。不同编码但视觉相同的资产不能简单放过，应使用明确的可验证等价规则；未知平台状态保持未证明。资源证明仍不混入裸创建 spec。

### [P2] AA-JSON-004 — 公开报告保留已识别的 Inspector 降级

位置：`/Users/long/GitHub/ASECLI/src/asecli/sg_export/evidence.py:33` 的 inspector_degradations；`sg_export/conversion_report.py:82` 的公开 degradations 构造。

内部报告会记录 CUSTOM_INSPECTOR_NOT_MIGRATED、INSPECTOR_METADATA_NOT_MIGRATED。公开报告只由 checks/failure 重建 degradations，不合并这些内部记录；properties 又只依据 semantic_mapping=passed 写 verified。

已验证：复用 `tests/test_export_sg.py` 的最小 Opaque ASE 夹具，将 Master 的 CustomEditor 设为 `MZGUI.MZGUI`，调用真实 build_candidate 和 cmd_export_sg。内部 degradations 包含 CUSTOM_INSPECTOR_NOT_MIGRATED；公开 report 只剩 SEM-EVIDENCE-001、SEM-COMPARE-001，properties=verified，而且 spec 已产出。

影响：接收方无法从唯一公开交接报告看见已知 Inspector 行为丢失。对纯展示元数据可能不影响像素，但 Custom ShaderGUI 还可能控制关键词/材质状态；本轮未断言夹具实际执行这些行为。

修复：将内部降级规范化为公开 report 的 rule/source/target/reason；区分只影响呈现的已知差异与影响渲染的未知外部消费者，并让对应语义状态/发布策略一致。不能直接清空降级信息。

### [P2] AA-JSON-005 — 拒绝自相矛盾的语义证据

位置：`/Users/long/GitHub/SGCLI/src/sgcli/native/conversion_gate.py:79` 的 `_report`。

消费者检查各 checks 为 verified、三个 producer evidence 为 passed，但完全不检查 degradations 是否与这些声明冲突。裸 JSON Schema 只验证形状，未约束此跨字段一致性。

已验证：在测试 report 中保留七项 verified，追加一项 `rule=SEM-RESOURCE-001, category=unsupported, reason=texture content changed`，更新 report/receipt 哈希绑定。certify 仍返回 true。这个反例模拟错误/过时生产者报告；不将能改全部文件的本地用户描述为通过了密码学签名。

修复：认证允许正常的下游 not_run/evidence_gap（如尚未开 Editor），但必须拒绝七项生产语义规则中 unsupported/语义变化与 verified 并存。生产者 assert_spec_publishable 也应使用一致的政策，避免输出消费者必拒绝的交接。
