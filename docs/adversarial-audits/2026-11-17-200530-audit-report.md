## 审计边界

- **范围**：`bridge_client.py`、`bridge_probe.py`、`codely_client.py`、`codely_discovery.py`、`codely_probe.py`、`backend.py`、`editor_result.py` 及默认 `auto` 行为
- **方法**：按「入口 → 鉴权 → 状态变更 → 持久化 → 副作用 → 失败/重试」逐面对抗遍历；每条发现均在真机（编辑器 pid 70407）或隔离进程内复现
- **本轮性质**：三轮递进审计，每轮聚焦不同攻击面，发现增量追加至本文件
- **威胁假设**：本机存在可写工程目录与用户目录的不可信进程；多工程并存；桥与探针会独立升级；调用方凭 CLI 输出判断成功与否

## 威胁与失败模型

- **资产**：ASE 资产正确性；CLI 结果可信度；邮箱队列可用性
- **攻击者能力**：可写 `Library/DSHBridge/**`（含 `instance.json`、`inbox/`、`outbox/`）；可命名与 ASECLI 请求同形的文件；可注入未来时间戳
- **最贵失败**：ASECLI 接受了不属于本次请求的"响应"，据此报告成功——而真实操作根本没执行

### 汇总

### [P1] AA-SEC-020 — 响应未校验归属 — `bridge_client.py:_read_response`

- **证据等级**：已验证
- **触发条件**：`outbox/` 中已存在与本次 `request_id` 同名的文件（伪造、撞号或历史残留）
- **错误行为**：`_read_response` 只检查 `isinstance(data, dict) and "ok" in data`，不校验 `instanceId` / `bootId` / `nonce` / `id`
- **复现**：

  ```
  预置 outbox/<rid>.json = {"ok":true,"data":{"result":"STALE-POISON"}}
  投递真实请求（脚本 return "REAL"）→ 客户端读到 "STALE-POISON"
  ```

- **影响**：调用方会把**从未执行**的操作当成成功。对 ASECLI 而言这意味着"建图/重编译报成功但资产未变"。探针侧虽然校验了请求的四元组，但客户端不校验响应，防护是单向的
- **最小修复方向**：读取响应后校验 `id`、`instanceId`、`bootId`、`nonce` 与本次请求一致，不一致则视为无效并继续等待
- **关联任务**：AA-OPT-020

### [P2] AA-DATA-021 — 未来时间戳使实例永不过期 — `bridge_client.py:instance_is_stale`

- **证据等级**：已验证
- **触发条件**：`instance.json` 的 `lastSeenAt` 被写成未来时间
- **错误行为**：`(current - stamp) * 1000 > threshold` 在 `stamp` 为未来时为负，恒不成立 → 永判新鲜
- **复现**：`lastSeenAt="2099-01-01T00:00:00Z"` → `instance_is_stale → False`
- **影响**：已死实例会一直被视为可用；`auto` 会反复选中它并失败
- **最小修复方向**：对负 age（时钟前移）做上限保护，超过阈值同样判 stale
- **关联任务**：AA-OPT-021

### [P2] AA-LOGIC-022 — 缓存键缺少 instance_token — `backend.py:select_backend`

- **证据等级**：已验证
- **触发条件**：同一进程内以不同 `instance_token` 调用 `auto`
- **错误行为**：`cache_key = (resolved_path, mcp_url, codely_port)`，不含 `instance_token` / `allow_remote_mcp`
- **复现**：`instance_token='userA'` 与 `'userB'` 命中同一缓存条目
- **影响**：A 的探测结论被 B 复用；若两个 token 指向不同 MCP 实例，会连错编辑器
- **最小修复方向**：把凭据相关参数并入缓存键
- **关联任务**：AA-OPT-022

### [P1] AA-DATA-023 — 迟到响应无限累积 — `bridge_client.py:execute_code` finally

- **证据等级**：已验证
- **触发条件**：客户端超时，但探针仍在执行并最终写 `outbox/`
- **错误行为**：客户端 `finally` 只删除自己的 `inbox` 请求，**不清理 `outbox` 里的迟到响应**；探针侧也无回收
- **复现**：

  ```
  投递 2.5s 脚本，timeout=0.3 → 超时
  等待 4s 后 outbox 中 req_asecli_* 残留 = 5 个（含历史累积）
  ```

- **影响**：长期运行会累积无损文件；更重要的是**这些残留正是 AA-SEC-020 的伪造源**——历史迟到响应可能被未来的同 id 请求读到（虽然 UUID 撞号概率极低，但配合伪造就成立）
- **最小修复方向**：取消/超时路径尝试清理自己的 `outbox` 条目；投递前清理本进程历史残留
- **关联任务**：AA-OPT-023

### [P2] AA-SEC-024 — 异常详情回显完整栈 — `bridge_client.py:_await` 错误分支

- **证据等级**：已验证
- **触发条件**：脚本抛异常，探针把 `detail`（含完整 stack trace）写入响应
- **错误行为**：客户端把 `error` 原样塞进 `BridgeError.data`，CLI 再输出
- **复现**：观察到 `detail` 含 `at __DshScript.Execute () [0x00000] in <...>:0` 等完整帧
- **影响**：CLI 输出被大量栈帧淹没；且栈中含本机路径。属信息卫生问题，非突破
- **最小修复方向**：错误消息只取首行，完整 detail 留在 `data` 供 `--verbose` 使用
- **关联任务**：AA-OPT-024

### [P2] AA-TEST-025 — 响应归属校验零覆盖 — `tests/test_bridge_transport.py`

- **证据等级**：已验证
- **触发条件**：审查现有 17 个 Bridge 测试
- **错误行为**：没有任何用例构造"`outbox` 预置他人响应"的场景；`stale` 相关断言只覆盖时间阈值
- **复现**：`grep -n "stale\|forged\|poison" tests/test_bridge_transport.py` → 无响应归属相关用例
- **影响**：AA-SEC-020 这类"防护是单向的"缺陷正是测试盲区放过的。测试只验证了 happy path 与少数失败分支
- **最小修复方向**：为每条 P1/P2 补一个对抗性用例（预置伪造响应、未来时间戳、迟到残留）
- **关联任务**：AA-OPT-025

### [P3] AA-LOGIC-026 — 缓存键使用未规范化中间路径 — `backend.py:cache_key`

- **证据等级**：已验证
- **触发条件**：目标路径含 `..` 或 `./`
- **错误行为**：`Path(target).resolve()` 对**不存在**的中间路径只做词法折叠，得到 `/Users/long/Tuanjie3D/Assets` 这类错误路径作为缓存键
- **复现**：

  ```
  '/Users/long/Tuanjie3D/P376/Assets'                     → 键 A
  '/Users/long/Tuanjie3D/P376/Assets/../../Assets'        → 键 '/Users/long/Tuanjie3D/Assets'
  两者不共用缓存
  ```

- **说明**：真实工程根解析由 `resolve_project_root` 重新推导，穿越会被拒绝（实测 `cannot locate a Unity project`），因此**不构成安全问题**，仅降低缓存命中率并产生无意义的缓存条目
- **最小修复方向**：缓存键统一用 `resolve_project_root` 的结果
- **关联任务**：AA-OPT-026

## 跨轮次的系统性观察

1. **单向信任**：探针严格校验请求四元组，客户端却完全不校验响应。信任边界只画了一半
2. **失败路径的资源卫生**：超时/取消路径普遍只清理"自己知道的"文件，忽略了对方会继续写入的事实
3. **测试的乐观偏置**：三轮里最严重的两个 P1 都在"外部主动构造异常状态"的场景，而测试都只覆盖了"自然发生"的路径

## 测试与观测缺口

- 缺失用例：伪造响应、未来时间戳、迟到残留、缓存键凭据隔离
- 缺失观测：未记录实际命中的 `request_id` 到 CLI 常规输出（仅错误时带）

## 残留风险

- `instance.json` 与 `inbox/` 完全可伪造，这是文件邮箱协议的固有属性，**ASECLI 侧只能做完整性校验，无法做身份认证**。已接受此前提
- 探针升级后协议漂移无自动检测（依赖 `probeVersion`/`sourceHash` 人工比对）

## 总评

- **结论**：**条件通过**（无 P0；有 2 个 P1 需修）
- **前置条件**：AA-OPT-020（响应归属校验）、AA-OPT-023（残留清理）、AA-OPT-021/022（边界加固）
