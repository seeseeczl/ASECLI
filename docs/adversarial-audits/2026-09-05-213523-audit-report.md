## Findings 详情

### [P1] AA-COMPAT-001 — 恢复 `McpClient` 第四位置参数的原有含义 — `src/asecli/bridge/mcp_client.py:69`

- 证据等级：已验证。
- 触发条件：调用方沿用 v0.4.0 的公开构造方式 `McpClient(url, token, 120.0, True)`，将第四位置参数作为 `allow_remote=True`。
- 错误行为：v0.4.1 把 `connect_timeout` 插入 `timeout` 与 `allow_remote` 之间，旧调用因此变为 `connect_timeout=True`、`allow_remote=False`。以远程 URL 动态复现时直接得到 `McpError: remote MCP URL requires --allow-remote-mcp`；loopback 调用则会把建连超时静默缩短为约 1 秒。
- 证据：v0.4.0 签名为 `(url, instance_token=None, timeout=120.0, allow_remote=False)`；当前签名位于 `src/asecli/bridge/mcp_client.py:69-75`。该类由 `src/asecli/bridge/__init__.py:3,22` 明确公开导出。`REL-0007:19` 同时声明兼容保持不变。
- 影响：第三方集成和旧自动化无需代码报错就发生参数错位；远程桥接完全不可用，loopback 在慢启动时产生新的间歇失败。当前仓库内部调用均使用关键字，现有测试因此无法暴露回归。
- 最小修复方向：保持 `allow_remote` 的第四位置不变，把 `connect_timeout` 放到其后并优先设为仅关键字参数；补充 v0.4.0 四位置参数兼容测试。
- 关联优化任务：AA-OPT-001。

### [P1] AA-GOV-001 — 让目录门禁覆盖验证列中的全部 pytest 命令 — `tools/check_regression_catalog.py:14`

- 证据等级：已验证。
- 触发条件：登记命令带前置环境变量或采用发布文档推荐的 `uv run --frozen pytest ...` 形式。
- 错误行为：正则只匹配反引号中精确以 `uv run pytest` 开头的内容。对当前目录统计得到 50 个包含 pytest 的反引号代码片段，但 `catalog_commands()` 只返回 41 个，稳定漏掉 9 个；其中包括 REG-0044、REG-0045、REG-0046 的普通 `--frozen` 自动测试以及 6 个条件 bridge 命令。脚本仍返回 `ok=true`。
- 证据：限制性正则在 `tools/check_regression_catalog.py:14`；检查结果计数仅为已解析项，`tests/test_governance.py:18-28` 只断言返回码与 `checked >= 15`，没有对账文档中的 pytest 片段总数。CI 又在 `.github/workflows/ci.yml:29-30` 通过全量 pytest 间接触发该门禁，已删除显式检查步骤。
- 影响：“每个 pytest 命令仍可收集”的治理承诺不成立；目录路径或 node id 失效可在 CI、发布检查和 `checked` 数字全部绿色时长期存在。`REL-0007:38` 明确把“聚合检查漏收集”列为停止条件，但当前门禁无法检测自身漏收集。
- 最小修复方向：结构化解析验证命令单元，识别环境赋值、`uv run` 选项和每个 pytest 子命令；用“文档 pytest 片段数 = 已解析数”硬断言拒绝静默遗漏。聚合时只合并测试 selector，带语义选项的命令按规范化命令分组。
- 关联优化任务：AA-OPT-002。

### [P2] AA-PROTO-001 — 将 socket 读超时归一化为 bridge 故障 — `src/asecli/bridge/mcp_client.py:94`

- 证据等级：已验证。
- 触发条件：MCP TCP 连接已建立并收到请求，但服务端在配置超时内不返回 HTTP 响应。
- 错误行为：`_post()` 仅捕获 `HTTPError` 和 `URLError`。本地停滞 socket 动态复现得到内建 `TimeoutError: timed out`，不是 `McpError`。CLI bridge 命令只把 `McpError` 转为 `BRIDGE_ERROR`，最终由总兜底输出 `INTERNAL` 并返回通用退出码 2，而不是 bridge 退出码 3。
- 影响：常见慢启动/挂起被错误分类，调用方无法按既有退出码重试或提示用户检查 Editor/MCP；本次“更快失败”的改动反而削弱了故障诊断。
- 最小修复方向：在传输边界显式捕获 `TimeoutError`/`socket.timeout` 并链式转换为脱敏 `McpError`，保留当前 HTTP/URL 错误语义。
- 关联优化任务：AA-OPT-003。

### [P2] AA-PERF-001 — 对整个 connect 使用单一截止时间 — `src/asecli/bridge/mcp_client.py:159`

- 证据等级：高置信推断。
- 触发条件：`initialize` 和 `notifications/initialized` 两个请求分别接近超时才返回或失败。
- 错误行为：两个 `_rpc` 调用各自获得完整 `connect_timeout=20.0`，因此一次 `connect()` 的最坏等待接近 40 秒，而不是用户容易理解的 20 秒连接预算。现有测试只断言两次都传入 20.0，实际固化了累计预算。
- 影响：MCP 不健康时一次 CLI 操作仍可能长时间无响应；与本次专门解决“随便改点东西也要二十分钟”的效率目标相悖，批量调用时会继续放大。
- 最小修复方向：在 `connect()` 开始时计算单一 monotonic deadline，第二阶段只使用剩余时间；错误中注明超时阶段和总预算。
- 关联优化任务：AA-OPT-004。

### [P2] AA-REL-001 — 使 `REL-0007` 的证据摘要和最终 CI 自洽 — `docs/04-delivery/releases/REL-0007-v0.4.1-private-release.md:31`

- 证据等级：已验证。
- 触发条件：人员或自动化把发布记录的 evidence 字段和证据摘要作为当前发布事实源。
- 错误行为：tag、Release、候选 CI、最终证据提交和本机安装已经完成，frontmatter 状态也已是 `released`，但正文 `:31` 仍写“远端证据待回填”；evidence 只列候选 run `33959329071`，未区分证据提交的最终 run `33959451750`。
- 影响：同一记录同时声称远端证据完成和待回填；审计人员无法只依据证据摘要确认候选构建与最终文档提交分别由哪个 CI 覆盖。
- 最小修复方向：移除待回填文案，明确区分候选提交 CI 与证据提交最终 CI，并记录 run `33959451750`。
- 关联优化任务：AA-OPT-005。

## 测试与观测缺口

- 缺少公开 `McpClient` 构造签名的向后兼容测试，尤其是旧四位置参数调用。
- 缺少真实 socket“已连接但无响应”测试；当前测试只检查 mock `_post` 收到的 timeout 数值。
- 缺少 `connect()` 总耗时预算测试以及 initialize/initialized 各阶段的错误标签。
- 回归目录测试没有 parser completeness oracle，也没有覆盖环境赋值、`--frozen`、多个 `uv run` 选项和一行多命令。
- CI 中目录门禁只作为 `tests/test_governance.py` 的子进程副作用出现，工作流日志不直接展示解析总数、目录总数及遗漏数。
- 发布记录缺少能阻止 `released` 与正文 pending 证据互相矛盾的静态治理规则。

## 残留风险

- 本轮只攻击 v0.4.1 快速路径；v0.4.0 的 MZGUI/fallback 跨环境真实 Editor 风险仍由此前审计与对应 E2E 边界管理。
- 即使修复目录解析，`--collect-only` 也只能证明测试可收集，不能证明条件 bridge 已在真实 Editor 环境执行。
- 120 秒 `tools/call` 是每次请求预算而非整条 CLI 工作流预算；未来增加多次 tool call 时仍需明确整体 deadline。
- 没有发现 P0 或当前仓库内部立即数据破坏路径，但两个 P1 已否定“公共兼容完全保持”和“目录完整覆盖”两项发布陈述。
