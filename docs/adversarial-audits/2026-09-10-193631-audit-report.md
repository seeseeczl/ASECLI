## 威胁与失败模型

- 资产：stdout 单行 JSON 的可解析性、`ok`/退出码语义、稳定错误码和 Agent 自动化的可恢复性。
- 攻击者能力：提供异常 Unicode 路径、包含 `nan`/`inf` 的 ASE 序列化、调用 argparse 内建动作，或依赖文档枚举实现错误处理。
- 最贵失败：命令实际失败却留下半截 JSON和 traceback，导致上层 Agent无法分类；或命令返回 exit 0/`ok=true` 但载荷不是标准 JSON并错误声称结构验证通过。
- 次级失败：新增命令和错误码绕过回归门禁，发布后才暴露契约漂移。
- 信任边界：ASE 文件内容进入 Python 浮点解析；任意 handler 返回值进入统一 JSON writer；终端编码决定最终字节输出。

## Findings 详情

### [P1] AA-DATA-001 — 强制 JSON writer 与终端编码解耦并保证失败也原子输出 — `src/asecli/cli/main.py:216-236`

- 证据等级：已验证。
- 触发条件：stdout 被配置为 ASCII 等不能编码响应中字符的编码，同时路径、错误消息或数据含中文等非 ASCII 字符。例如：`PYTHONIOENCODING=ascii PYTHONPATH=src uv run python -m asecli.cli.main parse 不存在.shader`。
- 错误行为：`json.dump(..., ensure_ascii=False)` 直接写 `sys.stdout`，且错误分支中的 JSON 写入本身不在可恢复保护内。复现得到退出码 1、stderr traceback，并在 stdout 留下 `{"ok": false, ... "message": "}` 半截 JSON，而契约要求错误退出码 2 和一个可解析 JSON 对象。
- 影响：任何严格 Agent 消费者都会在最需要错误信息时二次失败；半截输出还可能被日志聚合器误拼接到下一条消息。Windows、CI、重定向管道或显式 `PYTHONIOENCODING` 均可能触发，不仅是人为攻击。
- 最小修复方向：先在内存中以 `ensure_ascii=True`、`allow_nan=False` 序列化完整字节，再一次性写入 `sys.stdout.buffer`；将“生成 envelope + 序列化 + 写出”置于统一最外层，定义 writer 自身失败时的纯 ASCII 兜底和稳定退出码。
- 关联优化任务：AA-OPT-001。

### [P1] AA-DATA-002 — 拒绝非有限 ASE 数值并禁止输出 NaN/Infinity — `src/asecli/core/commentary.py:22-45`, `src/asecli/cli/main.py:224-236`

- 证据等级：已验证。
- 触发条件：输入 ASE 的 CommentaryNode 宽、高或坐标使用 Python 可解析的 `nan`/`inf` 文本。`float("nan")` 成功，且 `width <= 0` 对 NaN 为 false，现有正数门禁被绕过。
- 错误行为：隔离临时 Shader 将 Comment width 改为 `nan` 后，`comment-group` 返回 exit 0、`ok=true`、`structural_validation="passed"`，stdout 包含裸 `"width": NaN`。RFC 8259 JSON 不允许 NaN/Infinity；`json.dump` 默认 `allow_nan=True` 使统一 writer 没有最后防线。
- 影响：严格 JSON 解析器拒绝响应；更严重的是 CLI 把非有限几何标记为结构通过，后续布局、重叠比较和写回可能传播损坏值。
- 最小修复方向：所有从 ASE/Editor 解析的坐标、尺寸、padding、端口和布局浮点统一执行 `math.isfinite`；`parse_commentary_node` 至少拒绝非有限 position/width/height；统一 writer 设置 `allow_nan=False` 并把序列化失败映射为确定的 `INTERNAL`/数据错误，不能返回成功。
- 关联优化任务：AA-OPT-002。

### [P2] AA-CONTRACT-001 — 统一 help/version 与机器 JSON 契约边界 — `src/asecli/cli/main.py:33-44`, `src/asecli/cli/main.py:211-237`

- 证据等级：已验证。
- 触发条件：调用 `asecli --help`、`asecli --version` 或 `asecli parse --help`。
- 错误行为：argparse 的 help/version action 直接向 stdout 输出普通文本并抛 `SystemExit`；`app` 不捕获该出口。三条命令动态复现均 exit 0 且 stdout 不是 JSON。与此同时模块注释和 Skill 声明 stdout 恒为 JSON，没有公开例外。
- 影响：Agent 常用 `--version` 做能力探测，按项目公开契约执行 `json.loads` 会失败；相同 stdout 根据参数突然切换协议。
- 最小修复方向：明确选择一种协议并锁定：推荐让 `--version` 输出 JSON，help 明确作为唯一人类文本例外并写入契约；若坚持“恒为 JSON”，则自定义 help/version action 返回 JSON data，不走 `SystemExit` 旁路。
- 关联优化任务：AA-OPT-003。

### [P2] AA-CONTRACT-002 — 从实现生成并校验完整错误码目录 — `skills/asecli/SKILL.md:268-274`

- 证据等级：已验证。
- 触发条件：调用方按 Skill 公布的错误码集合实现分支，随后命中 layout、graph-review、schema version 或 Skill 安装错误。

- 影响：Agent 会把已设计的业务失败当未知错误；错误码已经是公共 JSON 契约的一部分，文档漂移会破坏可恢复策略和版本兼容判断。
- 最小修复方向：建立单一错误码注册表，代码抛错和文档/测试都从该注册表校验；至少增加“实现集合等于已发布集合”的测试，新增/删除错误码必须显式更新契约。
- 关联优化任务：AA-OPT-004。

### [P2] AA-TEST-001 — 修复 REG-0007 对“全部命令”的假覆盖 — `tests/test_cli_contract.py:1-27`, `tests/test_cli_contract.py:80-103`

- 证据等级：已验证。
- 触发条件：新增或修改 `graph-audit`、`graph-review`、`install-skill`、help/version、非 ASCII/非有限数输出路径，而开发者仅运行登记的 REG-0007。
- 错误行为：定向测试 24/24 通过，但“every command”参数表仅含 14 个命令，当前 parser 有 17 个，遗漏上述 3 个；没有 help/version、ASCII stdout、writer 失败或 NaN/Infinity 用例。测试使用 Python 默认 `json.loads`，默认还接受非标准 NaN，因此无法守住“合法 JSON”。
- 影响：质量目录把 REG-0007 标记为自动通过，但本次两条 P1 和协议旁路均未被发现；后续新增命令仍可能静默漏出契约门禁。
- 最小修复方向：从 `build_parser()` 动态枚举 subcommands，并为每个命令建立最小成功/失败契约矩阵；严格解析器拒绝非有限常量；加入输出编码、help/version、退出码、单对象单行和 stderr 脱敏断言。
- 关联优化任务：AA-OPT-005。

## 残留风险

- 本审计没有穷举每个 handler 的所有 data shape，也没有验证第三方 Agent 解析器对顶层附加 `data`、字段类型和未知错误码的兼容策略。
- `json.dump` 成功路径位于 handler try/except 之后；除编码和 NaN 外，未来 handler 返回不可序列化对象仍可能产生 traceback/部分 stdout。
- 当前 `HEAD` 不包含已回退的 ASE→SG JSON 导出，因此本报告不能作为该导出能力的安全或正确性证据。
