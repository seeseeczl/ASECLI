# 对抗性审计报告 — ASECLI 是否具备「shader 切换渲染管线」能力

- 时间戳：2026-10-14-163548
- 审计对象：`/Users/long/GitHub/ASECLI` 工作树（HEAD `01e84d6`，v0.8.6，工作区干净）
- 审计问题：本工具现在具不具备把一张 shader 从 URP 换成 HMIRP（或任意其它管线）并保证连接正确的能力
- 审计性质：**能力边界判定审计**（capability audit），非回归审计
- 环境约束：用户已明确「现在没有测试环境」，因此本次不启动 Unity/团结、不跑 bridge 标记测试；全部结论基于源码、Schema、契约快照与离线可执行验证
- 方法：入口 → 校验 → 状态变更 → 持久化 → 失败路径 全链路静态遍历 + 离线可执行探针（`.venv/bin/python` 直接调用 loader）
- 发布建议：**阻塞**（对该能力而言为「能力不存在」，非「有缺陷待修」）

---

## 1. 结论摘要

**能力层面判定：不具备。** ASECLI 当前是一个**单管线（URP Unlit）绑定**的图写入/导出工具，它没有任何「管线」这一维度的一等概念，因此既不能切换管线，也不能在切换后保证连接正确。

具体地，一个「URP shader → HMIRP shader」的操作需要三件事，ASECLI 三件都不做：

| 需要的能力 | ASECLI 现状 | 证据 |
| --- | --- | --- |
| ① 识别源 shader 属于哪个管线 | 只能识别「是不是那一个 URP Unlit 模板 GUID」，识别不出「是什么管线」，也不认识 HMIRP | `sg_export/model.py:19`、`sg_export/decoder.py:185` |
| ② 用一个 HMIRP 模板重建图 | 模板 GUID 必须**恰好等于** `2992e84f91cbeb14eab234972e07ea9d`，否则校验期直接抛错；没有任何 HMIRP 模板契约 | `bridge/_editor_port_contract.py:85`、`bridge/render_settings.py:18`、实测见 §4.1 |
| ③ 保证重建后连接正确 | Master 端口映射表是**该 URP Unlit 模板专属的硬编码常量**；换模板后端口语义未知，工具没有任何机制去保证，只会整体拒绝 | `bridge/_editor_port_contract.py:13-22` |

**关于「原地改管线」——初版报告在此处的判断是错的，已更正。** `create` 确实只支持「目标资产必须不存在」（Editor 后端），`--force` 被显式禁止：

```python
# src/asecli/cli/create_command.py:114-115
if args.force:
    raise CliError("USAGE_ERROR", "editor create only supports absent targets; --force is not allowed")
```

初版据此推断「不存在原地改管线的路」，**这是错误的**。`create` 只是**受控**入口的封闭，而 `set-field` 是**通用的原始字段写入**入口，它可以直接改写 Master 的模板 GUID 字段（field 13），且下游结构校验与 `export-sg` 都不会阻断。详见 **AA-TARGET-009**（P1，本次补充审计新增，已实测）。

因此准确表述是：**ASECLI 有原地改管线的"手段"，但没有"能力"**——它能改那一个字段，却不理解改完之后图是否还成立，也不做任何适配或验证。对批量改管线这个具体诉求，这构成了一个**伪成功**路径，比"不支持"更危险。

**这不是缺陷，而是已声明的设计边界。** 需求文档明确写死第一期范围：

> `docs/proposals/2026-09-07-shadergraph-to-ase-requirements.md:220`
> - 第一期只支持 ASE 1.9.6.2 + URP Unlit 模板 GUID `2992e84f91cbeb14eab234972e07ea9d`。
> :200 `不要第一期做 HDRP、Keyword、完整 Lit Stack、动画/材质升级迁移工具。`

README 也如实声明了 URP Unlit 是唯一开放模板（`README.md:324`）。

**因此本次审计的价值不在于「发现了漏洞」，而在于：把这个「不具备」从「文档里的一句话」升级为「有逐行证据、且指出了若要补齐会在哪里断」的工程结论。** 下面 §3 的发现全部是「在补齐 HMIRP 时会被踩到的具体断点」，而不是对现状的指控。

## 2. 审计边界与威胁假设

### 2.1 在范围内

- `create --spec`（Editor 后端）的模板准入、Master 端口契约、创建后回执校验

- 模板选项（render settings）的应用与回读校验
- 端到端「管线」概念的代码表示（有无）

### 2.2 不在范围内

- HMIRP 本身的定义、模板 GUID、Pass 集合、ShaderGUI：**仓库内不存在任何 HMIRP 痕迹**（全仓 `grep -ri hmirp` 与 `grep -ri HMI` 均为零命中），无法审计一个不存在的东西
- 真实 Editor 行为：按用户要求与 AGENTS.md「Editor 与截图按需执行」，本次不启动引擎
- SGCLI 仓库内部实现：只做只读旁证（见 §4.4），不修改、不作为结论依据

### 2.3 威胁假设

本能力的「最贵失败」不是崩溃，而是**静默产出错误结果**：

- 假设 A（已证伪）：工具接受一个非 URP 模板 GUID，然后在端口映射未知的情况下「尽力而为」地连出一张能编译、但语义错误的图 → **伪成功**。这是本类工具最严重的失败形态。
- 假设 B（已证实为设计意图）：工具在校验期整体拒绝非 URP 模板 → 失败关闭。这是可接受的安全失败。

**审计的核心问题因此确定为：工具是否在任何一条路径上「接受了非 URP/HMIRP 模板并继续往前走」。** 见 §3 的 `AA-TARGET-001`。

### AA-TARGET-001 — 模板身份与**管线身份**在类型系统里被合并，管线不可表达（P2，已验证）

- **域**：产品逻辑 / 架构
- **证据等级**：已验证（源码 + 离线探针）

**触发条件**：任何需要「按管线选择模板」的调用，例如给一个 HMIRP 模板 GUID 让 `create` 建图。

**错误行为**：代码里不存在「管线」这个类型或字段。模板身份唯一由 32 位 hex GUID 承载（`bridge/editor_spec.py:14-21` `TemplateSpec{guid, shader_name, settings}`），而全仓只有**一个** GUID 被赋予语义：

```python
# src/asecli/bridge/_editor_port_contract.py:12
_URP_UNLIT_GUID = "2992e84f91cbeb14eab234972e07ea9d"
# src/asecli/sg_export/model.py:19
URP_UNLIT_GUID = "2992e84f91cbeb14eab234972e07ea9d"   # 同一个字面量，第二份拷贝
```

`_URP_UNLIT_GUID` 这个名字本身就把「管线」和「模板」压成了一件事。同理 `render_settings.py:18` 再抄第三份字面量、`core/compiled_metadata.py:22` 抄第四份（字典 key）：

```
2992e84f91cbeb14eab234972e07ea9d 出现的生产代码位置：
  src/asecli/bridge/_editor_port_contract.py:12
  src/asecli/bridge/render_settings.py:18        (字面量，非引用常量)
  src/asecli/core/compiled_metadata.py:22        (字典 key，非引用常量)
  src/asecli/sg_export/model.py:19
```

**为何重要**：这不是「命名不好看」的风格问题（本 skill 明确不报风格债），而是**扩展成本的结构性事实**：要支持 HMIRP，必须新增的不是「一个 GUID 常量」，而是一整套并列的 `{模板 GUID → Master 端口表 → 模板选项表 → 编译期专有属性表 → Pass 集合}` 五元组，而当前这五元组散落在 4 个模块里、以裸字面量和全局单例的形式存在，没有一处可以按模板分发。补齐时任何一处漏改，都会退化成 §假设 A 的伪成功。

**当前是否会误用**：否。四处字面量值一致，且 §4.1 的探针证明未知 GUID 会被拒绝。故定级 P2（真实缺陷，局部/特定条件），而非 P1。

### AA-TARGET-002 — `export-sg` 面对非 URP 模板时，诊断是**累积式**的，存在「报告失败但仍继续构建候选图」的路径（P2，高置信推断）

- **域**：失败路径 / 产品逻辑
- **证据等级**：高置信推断（已读完整控制流；未在真实非 URP 资产上执行，因无测试环境）

**触发条件**：对一个模板 GUID ≠ URP Unlit 的 ASE shader 执行 `asecli export-sg`。

**错误行为**：`_target()` 在检测到非 URP 模板时**只追加诊断，不抛异常，也不提前返回**：

```python
# src/asecli/sg_export/decoder.py:181-187
def _target(master, diagnostics):
    if master is None:
        return {"model": "Unlit", "surface": "Opaque", "blend": "Alpha", "two_sided": False}
    fields = master.raw_fields
    if len(fields) < 16 or fields[13] != URP_UNLIT_GUID:
        diagnostics.append(diagnostic(master.node_id, "TARGET_UNSUPPORTED",
            "only the certified standard URP Unlit template is supported", "Target semantics cannot be preserved"))
    # ← 没有 return / raise，继续往下走
```

随后 `decoder.py:199` 起仍然按 URP Unlit 的选项标签（`"Surface"` / `"  Blend"` / `"Two Sided"`）去解析这个**未知模板**的 `raw_fields`：

```python
    surface = _template_option(fields, "Surface", ("Opaque","Transparent"), diagnostics, master.node_id)
    blend   = _template_option(fields, "  Blend", ("Alpha","Premultiply","Additive","Multiply"), ...)
```

**为何重要**：对一个 HMIRP/HDRP 模板，这些标签很可能存在但**语义不同**（例如 HDRP 的 Blend 模式集合、Surface Type 的取值域与 URP 不同）。`_template_option` 只要在字段里唯一匹配到同名标签、且其后的整数落在 `len(choices)` 范围内，就会**返回一个看起来合法的值**——于是 `target_spec` 被填上一个「URP 语义的值」，候选图照常构建。

**这是否构成实际漏洞？** 报告层面不是：`decoder.py:187` 的 `TARGET_UNSUPPORTED` 诊断最终会让 `assert_spec_publishable` 拒绝发布：

```python
# src/asecli/sg_export/conversion_report.py:25-40
def assert_spec_publishable(report):
    unknown = [name for name in CHECK_RULES
               if report.get("checks", {}).get(name, {}).get("status") != "verified"]
    ...
        raise ValueError("formal specification is not publishable; unverified semantics: " + ...)
```

**但证据等级上仍记为一条发现**，理由是两点可证伪的隐忧：

1. **浪费在错误语义上的工作**：`build_candidate` 会在明知 target 不可信的前提下，完整地遍历全部节点、产出 mappings、甚至可能改写表面语义（`normalize_surface_outputs`，`decoder.py:126`），最后才由 `assert_spec_publishable` 一票否决。中间产出的 `report["mappings"]` 会包含基于错误 target 推出的端口映射。
2. **审计/人工复核时的误导风险**：失败报告里同时存在「结构映射成功」的 mappings 和一条 `TARGET_UNSUPPORTED`。`TARGET_UNSUPPORTED` **不在** `_SEMANTIC_CODES` 集合中（该集合只有 4 个 `ALPHA_*`/`PASS_BLEND_*` 码，见 `report_semantics.py:17-20`），因此它只会以「第一条诊断」的兜底形式出现在 evidence 文本里，而不是作为显式的语义降级条目。人工看到 mappings 非空时存在误读为「部分成功」的空间。

**建议对照**：`_editor_port_contract.py:85` 在同类情形下是**抛异常**（失败关闭），两条路径的严格度不一致。

### AA-TARGET-003 — Master 端口类型契约是「宽度宽松」的，数值类型之间无差别放行（P3，已验证）

- **域**：正确性 / 边界
- **证据等级**：已验证（离线探针实测）

**触发条件**：向合法 URP Unlit 模板的 Master 端口写一条**类型不匹配但同属数值族**的连接。

**错误行为**：`_compatible_port_types` 对任意两个数值类型一律放行：

```python
# src/asecli/bridge/_editor_port_contract.py:126-133
def _compatible_port_types(source: str, destination: str) -> bool:
    if source == _DYNAMIC_NUMERIC: ...
    if destination == _DYNAMIC_NUMERIC: ...
    if source in _NUMERIC_TYPES and destination in _NUMERIC_TYPES:
        return True        # ← FLOAT3 → FLOAT 放行、FLOAT4x4 → FLOAT 也放行
    return source == destination
```

`_NUMERIC_TYPES` 含 `INT, FLOAT, FLOAT2, FLOAT3, FLOAT4, COLOR`。

**实测**（离线探针，`.venv/bin/python`）：向 `master port 2`（契约声明为 `FLOAT3` Color）送一个 `FLOAT` 源，**被接受**。

**为何重要**：对当前唯一的 URP Unlit 模板，ASE 自身在 Editor 侧会做隐式提升，实际上不产生错误（既有的 REG-0029/REG-0053 真机证据也支持这一点）。所以这不是当下会炸的 bug，定级 P3。它成为问题的场景正是**引入第二个模板**：不同模板端口的宽严不同（例如某端口的 `FLOAT` 会被当作 alpha 而非强度），此时「数值间一律放行」不再安全。也就是说 —— **这条宽松规则是当前"能用"的原因，也恰好是将来切管线时"静默连错"的入口**。

### AA-TARGET-004 — 模板 GUID 的「管线」语义没有任何机器可读的注册表，`settings` 又是可选的，导致模板身份无人把关（P3，已验证）

- **域**：契约 / 配置漂移
- **证据等级**：已验证

**触发条件**：构造一个合法 32 位 hex 的 GUID（如 `1111...`）且**不带** `settings`。

**实测结果**（离线探针）：

```
unknown-guid-no-settings   : rejected -> connections[0] template guid has no verified master-port contract
unknown-guid-with-settings : rejected -> render settings require the verified URP Unlit template
```

**分析**：两条路径都被拒绝了 —— 这是**正确行为**，工具是安全的。但拒绝的**理由不同、且都属偶然**：

- 无 `settings` 时，拒绝来自「只要有任何一条连到 master 的连接，就要求 GUID 匹配」（`_editor_port_contract.py:85`）。**若图里碰巧一条 master 连接都没有（例如只有一个孤立节点 + 零连接），这条防线不会触发**——此时未知 GUID 会被接受，一直走到 Editor。
- 有 `settings` 时，拒绝来自 render_settings 的白名单，但这要求用户恰好传了 `settings`。

也就是说：**「模板是不是被支持的模板」这件事，没有一处集中校验；它是被端口校验和 settings 校验的副作用顺带挡住的。** 对当前的 URP Unlit 单模板，这些副作用覆盖得足够好（实测两种构造都被拒）；但这是**偶然完备**而非**设计完备**，在增加第二个模板时它会立刻变成真问题。

**补充证据**：Schema 层也不管 —— `contracts/editor-graph-spec.v3.schema.json:40` 只约束 `"pattern": "^[0-9a-fA-F]{32}$"`，任意 hex 都合法。

### AA-TARGET-009 — `set-field` 可原地改写模板 GUID，下游零阻断，构成「批量改管线」的伪成功路径（**P1，已验证**）

- **域**：数据完整性 / 滥用 / 产品逻辑
- **证据等级**：已验证（真实 fixture 上实测）
- **来源**：第二轮补充审计（用户追问「批量把旧 shader 的管线设置改成新管线」）

**触发条件**：对任何已有 ASE shader 执行 `asecli set-field <file> --node <master_id> --field 13 --value <新模板GUID> --write`。

**错误行为**：`set_node_field` 只保护字段 0-2（marker/type/id），**field 13（模板 GUID）完全可写**：

```python
# src/asecli/core/graph_ops.py:9-22
def set_node_field(graph, node_id, field_index, value):
    if field_index in {0, 1, 2}:
        raise ValueError("fields 0-2 are structural (marker/type/id) and cannot be changed with set-field")
    node = graph.node_by_id(node_id)
    ...
    node.raw_fields[field_index] = value   # ← field 13 无任何校验
    graph.replace_node(node)
```

**实测（真实 fixture `tests/fixtures/HLIT.shader`，10 个 TemplateMultiPassMasterNode）**：

```python
# 把全部 10 个 master 的 f13 改成一个虚构 GUID
for m in masters:
    set_node_field(f.graph, m.node_id, 13, "abcdefabcdefabcdefabcdefabcdefab")

validate_file(f)   # → error: 0, warning: 1
```

**结果：结构校验报 0 error。** 一张模板 GUID 已被改坏、Master 语义已失效的图，在 ASECLI 自己的校验器眼里是"结构完好"的。

**为何重要 —— 这是本审计中最该优先修的一条**：

1. **它正好命中用户提出的真实诉求**。「批量把旧资产的管线设置改成新管线」听起来就像「改一个 GUID 字段」，而工具**恰好提供了这个手段**，且不报错。
2. **下游也拦不住**。`export-sg` 对改写后的 master 调用 `_target()`，实测只产出诊断、**不阻断**，并且仍然按 URP Unlit 的选项标签解析出看起来合法的 target：

   ```
   target = {'model': 'Unlit', 'surface': 'Opaque', 'blend': 'Alpha', 'two_sided': False,
             'options': {'castShadows': True, 'receiveShadows': True, 'supportsLodCrossFade': True}}
   诊断 = ['TARGET_UNSUPPORTED', 'TARGET_UNSUPPORTED', 'TARGET_OPTION_UNSUPPORTED']
   ```

   注意 `_target()` 的默认返回值（`decoder.py:183`）是 `{"model": "Unlit", ...}`——**它不会因为模板改了而改变，它只会返回 URP Unlit 的语义**。即：改完 GUID 后导出，得到的是一份"声称是 URP Unlit 语义"的 spec。
3. **与 AA-TARGET-001 的根因同源**：GUID 承载了"管线"语义，而没有任何一处把 GUID 的合法性当作一等校验对象。写路径（`create`）靠副作用偶然挡住了，**原始字段入口则完全没有挡**。
4. **批量放大**：`set-field` 是单文件命令，但它极易被脚本循环调用；一旦批量执行，损坏的是**整个资产目录**，且 `validate` 会告诉你"全部通过"。

**注意边界（避免夸大）**：`set-field` 本身是**有意的低层原始写入能力**，`graph_ops.py` 的注释也表明作者知道 0-2 是结构字段。本发现**不是**说"不该有 set-field"——原始写入能力对工具是必要的；问题是**它只保护了 3 个字段，而 field 13 在语义上是与这 3 个同级甚至更关键的身份字段**，却没有受到同等保护，也没有任何"你正在改模板身份"的提示或二次确认。此外，改坏后 ASE Editor 打开时的真实表现未经实测（无测试环境），但由 `editor_create.part03.cs.txt:12` 的 `reloadedMaster.CurrentTemplate.GUID != templateGuid` 校验可知，ASE 侧是把模板 GUID 当作**必须一致的身份**对待的。

### AA-TARGET-005 — Editor 创建回执校验里，模板 GUID 是**自反比较**，未与"已认证模板"比对（P3，已验证）

- **域**：失败路径 / 验证有效性
- **证据等级**：已验证

**触发条件**：Editor 端返回的 manifest 与请求一致，但两者基于同一个未被认证的模板 GUID。

**错误行为**：

```python
# src/asecli/bridge/editor_create.py:185-187
expected_template = expected_manifest["template"]
if response.get("template_guid") != expected_template["guid"]:
    raise McpError("Editor create returned a different template guid")
```

这里比的是 `响应 GUID == 请求 GUID`，**不是** `响应 GUID ∈ 已认证模板集合`。它是一个「一致性」校验，不是「合法性」校验。

**为何重要**：这本身是合理的分层（合法性应在 Python 侧的 spec loader 把关），但**前提是 loader 真的把关了**——而由 AA-TARGET-004，loader 的把关是「副作用式」的、存在零连接图的缺口。两者叠加后，**唯一的硬闸门是 `expected_manifest` 的自反比较**，这在模板维度上是空的。

`SUPPORTED_ASE_VERSIONS`（`editor_spec.py:10`，只有 `{"1.9.6.2"}`）证明团队有「白名单校验」的正确模式，只是没用在这一处。

### AA-TARGET-006 — "保证连接正确"这个目标在工具内**无独立证据链**，Manifest 只证明"我按你说的连了"（P2，已验证）

- **域**：验证有效性 / 产品逻辑
- **证据等级**：已验证

**触发条件**：用户诉求为「切换管线**并保证连接正确**」。

**错误行为**：`expected_manifest()` 的结构决定了它证明不了"连接正确"：

```python
# src/asecli/bridge/editor_spec.py:232-237
def expected_manifest(self) -> dict:
    return {
        "template": self.template.to_dict(),
        "nodes": [node.manifest_entry() for node in self.nodes],
        "connections": [item.to_dict() for item in self.connections],
    }
```

`manifest_entry()`（`editor_spec.py:124-176`）只记录 `alias/kind/type/…`，**不记录任何端口的语义或类型**；`connections` 原样回抄请求中的 `{node, port}`。创建后的校验是：

```python
# src/asecli/bridge/editor_create.py:196
if not manifests_match(response.get("manifest"), expected_manifest): ...
```

即 **「回读结果 == 请求内容」**。这条链能证明的命题是：「ASE 确实按我给的端口号连了线，且重载后没变」。

它**不能**证明的命题是：「端口 2 在这张图里确实代表 Color / BaseColor」。后者是**外部知识**，来源是 `_URP_UNLIT_MASTER_INPUTS` 这张手写表——而这张表没有任何 vacabulary 把端口号绑定到 `MASTER_OUTPUTS`：

```python
# src/asecli/bridge/_editor_port_contract.py:13-22  ← 手写：0..7
# src/asecli/sg_export/model.py:24-29               ← 另一份：0..7 → SurfaceDescription.*
MASTER_OUTPUTS = {
    0: "SurfaceDescription.BakedGI", 1: "SurfaceDescription.Emission",
    2: "SurfaceDescription.BaseColor", 3: "SurfaceDescription.Alpha", ...
}
```

两份表在数值上一致（0=Baked Albedo/BakedGI，2=Color/BaseColor，3=Alpha/Alpha…），但**分属两个模块、两个方向、无交叉校验测试**。这正是「切换管线」最危险的断言类型：端口号在新模板上含义完全不同，而工具的全部正确性都寄托在「有人手工维护了正确的对照表」上。

**结论**：即使将来补上 HMIRP 模板，如果只补 GUID 和端口表，「保证连接正确」仍然是**人肉保证**，工具不产出可独立核查的端口语义证据。这是本诉求下最需要补齐的一环。

### AA-TARGET-007 — 端到端切换路径中，`recompile` 是**唯一**的最终验证手段，且它不做语义校验（P3，已验证）

- **域**：运维 / 验证
- **证据等级**：已验证

`create`（Editor 后端）**不会**重新加载目标图——`target_graph_reloaded` 恒为 `false`（`README.md:326` 明示）。README 要求「CLI 属性收尾后必须使用独立 `recompile` 完成目标图重载复验」。

而 `recompile` 的 C# 片段（`bridge/recompile.py:17-60`）只做：加载 shader → 若 `CurrentGraph`/`CurrentMasterNode` 为空则抛错 → `SaveToDisk` → 返回 `"recompiled, saved=" + saved`。

**它不检查**：模板 GUID、Master 端口连接、Pass 集合、任何语义。因此**在管线切换场景下，"重载复验"通过只证明"ASE 能打开并保存这张图"**，不证明新模板的端口被连对了。

这意味着即使补齐 HMIRP，端到端链上仍然缺一个「新模板语义校验」环节。

### AA-TARGET-008 — 两条主路径的「模板准入严格度」不对称（P3，已验证）

- **证据等级**：已验证

## 5. 总评

**能力判定：不具备，且这是有意为之的设计边界，实现上做到了诚实的失败关闭。**

正面评价（有证据支撑，非客套）：

- 四条通往非 URP 模板的路径里，**三条是硬拒绝**（`_editor_port_contract.py:85`、`render_settings.py:18`、`schema` + loader），实测均生效
- `assert_spec_publishable` 是一道**真正的证据门禁**，不会因为「结构通过」就放行语义未证明的 spec
- README:324、需求文档:220、REG-0053 证据边界都**如实声明了 URP Unlit 是唯一模板**，没有夸大能力——这一点在同类工具里并不常见
- 真机证据（REG-0029/REG-0053）明确区分了「结构通过」与「画面通过」，没有冒充

需要正视的结构性事实：

- ASECLI 目前不是「多管线图工具」，而是**「URP Unlit 图工具 + 单管线绑定的转换契约」**。
- 它的正确性建立在**手写端口对照表**之上（`_URP_UNLIT_MASTER_INPUTS` / `MASTER_OUTPUTS`），而工具本身**不产出可独立核查的端口语义证据**（AA-TARGET-006）。这意味着「保证连接正确」在当前架构下是**人肉保证**，不是机器保证。
- 「管线」这一维度在代码里**不可表达**（AA-TARGET-001）。支持 HMIRP 不是"改一个常量"，而是要引入一个跨 4 个模块的五元组（模板 GUID / Master 端口表 / 模板选项表 / 编译期专有属性 / Pass 集合）并把它参数化。

**若要补齐该能力，最小可信路径**（详细任务见配套优化计划）：

1. 先把「模板注册表」做成单一事实源，把散落的 4 处 GUID 字面量与 2 份端口表收拢（消除 AA-TARGET-001/004/005 的根因）
2. 再补「端口语义证据」：让 spec/manifest 携带声明式端口类型，并让创建回执能独立校验（消除 AA-TARGET-006）
3. `export-sg` 的模板准入改为与写路径同等严格（AA-TARGET-002/008）
4. **在拿到真实 HMIRP 模板之前，不要先写端口表**——按 AA-TARGET-006，猜出来的端口表会制造「通过门禁的错误图」，比不支持更危险

**发布建议：阻塞。** 阻塞对象是「宣称具备 shader 管线切换能力」这一主张；对 ASECLI 现有的 URP Unlit 能力，本次审计**未发现可发布的阻断性缺陷**。
