## 威胁与失败模型

- 资产：Shader 的唯一 `CustomEditor` 选择、折叠/Tooltip/HelpBox 元数据、属性中文显示名，以及 ASE 图可再次编辑的能力。

- 最贵失败：工具或 ASE 保存成功，但三个状态副本中保存 GUI 身份/元数据的副本被覆盖，下一次 Inspector 静默回退为默认 GUI；用户误以为配置已经持久化。

## Findings 详情

### [P1] AA-DATA-001 — 将 GUI 持久化从“CLI 重编译后补丁”升级为可恢复的单一真相 — `src/asecli/cli/commands.py:225-245`

- 证据等级：高置信推断。
- 触发条件：用户直接在 ASE 编辑器中打开并保存一个带 ASECLI GUI 元数据的 Shader，或使用未经过 `asecli recompile` 的 ASE 保存入口。
- 错误行为：唯一的保存后恢复入口是 `cmd_recompile()`：它在 MCP 调用前快照、在调用后回填。已安装的 `ASECLIMaterialGUI` 只继承 `ShaderGUI` 并在 Inspector `OnGUI` 读取元数据；项目中不存在捕获 ASE 资产保存/导入并恢复数据的 `AssetModificationProcessor`、`AssetPostprocessor` 或独立持久化存储。`sync_compiled_property_metadata()` 只是 CLI 内存对象写盘前的同步，不会拦截手工 ASE 保存。代码注释还明确承认“一些 editor builds 保存时会丢弃自定义 PropertyNode attributes”（`core/compiled_metadata.py:83-89`）。因此手工保存可以跳过全部补偿机制。
- 影响：这与“打开保存就丢失”的表象高度吻合。CustomEditor、PropertyNode 尾部和编译区属性都是同一 Shader 资产内、由 ASE 可能重写的副本；一旦它们同时被重写，之后没有足以恢复原内容的真相源。
- 最小修复方向：为 ASECLI 管理的 Shader 建立与 Shader GUID 绑定的持久化 manifest（包括 GUI provider、稳定属性标识、显示名与三类新/旧标记）；在 Editor 的保存前捕获/保存后导入恢复链路中使用该 manifest。CLI `custom-gui` 和 `recompile` 都必须读写同一 manifest。若当前 ASE API 不提供可靠的保存后时机，应在命令和文档中明确禁止手工保存并让 GUI 显示可见告警，不能继续声称已持久化。
- 关联优化任务：AA-OPT-001。

### [P1] AA-DATA-002 — 无属性时仍必须快照并恢复 ASECLI CustomEditor — `src/asecli/cli/recompile_metadata.py:26-36`

- 证据等级：已验证。
- 触发条件：Shader 已设置 `ASECLI.MaterialGUI.ASECLIMaterialGUI`，但暂时没有 `ASECLI*` PropertyNode 标记；或仅包含旧 `FoldoutMzgui`/`TooltipMzgui`/`HelpBoxMzgui` 标记。
- 错误行为：`snapshot_recompile_metadata()` 只收集类型以 `ASECLI` 开头的属性（第 28-31 行），并在属性数组为空时返回 `None`（第 34-35 行）。`cmd_recompile()` 因此完全跳过 `restore_recompile_metadata()`。动态反例分别输出 `editor_only_snapshot= None` 和 `legacy_only_snapshot= None`。也就是说，恢复 CustomEditor 的逻辑被错误地绑在“至少一条新协议属性存在”上；旧标记虽然在 C# 与检查器中声明为可读兼容，却不属于重编译恢复范围。
- 影响：ASE 在此次保存中若重置/删除 CustomEditor，CLI 会报告重编译成功而不恢复 GUI；旧工程的 GUI 标记同样更容易丢失。这是无需手工保存、仅执行公开 `recompile` 命令即可触发的数据丢失路径。
- 最小修复方向：快照条件改为“存在 ASECLI GUI 身份或任何新/旧受管标记”；独立记录 graph 与 compiled 的 editor 值，并纳入三类 legacy 标记。恢复后必须检查两处 editor 一致、受管标记数与快照一致，否则返回专用持久化错误而不是成功。
- 关联优化任务：AA-OPT-002。

### [P2] AA-FAIL-003 — 用稳定属性身份恢复，不要用唯一可变名称赌成功 — `src/asecli/cli/recompile_metadata.py:45-50`

- 证据等级：已验证。
- 触发条件：ASE 保存/重编译同步改变了 Property 名称，或目标图删除/合并了某个属性。
- 错误行为：快照只存 `name`，恢复以 `resolve_property_node(..., property_name=prop["name"])` 精确查找。最小反例将 `_BaseColor` 改为 `_BaseColour`，稳定得到 `ValueError: expected one exported property named '_BaseColor', found 0`。此时 MCP 侧保存已经完成，而 `cmd_recompile()` 没有回滚该编辑器写入的事务；文件保持在元数据尚未恢复的状态。
- 影响：正常的图演化会把“应该显式提示并保全证据”的情况变成保存后失败；如果调用者只看编辑器而忽略 CLI 错误，表现仍是 GUI 消失。名称也是用户可编辑字段，不适合作为恢复唯一键。
- 最小修复方向：manifest 以 ASE PropertyNode ID 加 property name 双重身份记录；恢复时先按 ID 校验类型和名称，再有条件地使用唯一名称迁移。任何未匹配项都必须输出完整未恢复清单、保留 manifest/备份，并返回 `GUI_PERSISTENCE_ERROR`。增加显式“属性改名迁移”而不是静默重绑。
- 关联优化任务：AA-OPT-003。

## “两套 GUI 冲突吗？”的判定

- 不是本轮发现的主因。一个 ShaderLab Shader 只能有一条有效 `CustomEditor`；代码会把图主 Master 和编译区 `CustomEditor` 同步为同一个值，并对重复编译指令失败关闭（`core/custom_gui.py`）。
- ASECLI 与旧 MZGUI 是两个可能的 provider，但它们不会在同一个 Shader 上同时作为 `ShaderGUI` 运行。若保存后 `CustomEditor` 被改成 `MZGUI.MZGUI` 或其他值，ASECLI GUI 自然不会被调用；这是“提供者被覆盖”，不是两个 GUI 同时竞争渲染。
- 旧 MZGUI decorator 的短名称碰撞已被专门处理：ASECLI 的 C# 在缺少属性反射 API 时从当前 Shader 源文本补读旧标记；真实 E2E 还构造了原生同名 drawer 碰撞（`tests/test_material_gui_e2e.py:163-202`）。`gui-support` 也刻意允许工程内存在旧 MZGUI 文件（`tests/test_gui_support.py:187-196`）。因此“安装两个 GUI 文件”本身没有被证据证明为丢失根因。
- 真正的冲突是“谁拥有状态”：ASE 的保存器拥有 Shader 文件写权，而 ASECLI 只在自己的 CLI 重编译分支做事后修补，并没有独立、可恢复的持久化层。

## 测试与观测缺口

- 缺失用例：ASECLI CustomEditor 无任何属性标记、仅 legacy 标记、以及混合新旧标记的 `recompile` 保存后 editor/图尾部/编译属性三方一致性。
- 缺失用例：真实 Unity/Tuanjie 新进程 E2E：打开已管理 Shader → ASE SaveToDisk → 刷新/重开 → 断言 CustomEditor 和所有 GUI 元数据仍存在。现有 E2E 验证读取和新建，不验证“已有受管 Shader 被 ASE 再保存”。
- 缺失用例：属性重命名、删除、重复名时的恢复诊断与 manifest 保留；当前 85 项相关回归全部通过，未覆盖这些反例。
- 缺失观测：用户工程应在一次失败后采集保存前/后 shader SHA-256、`asecli custom-gui <file>` JSON、ASE/Unity Console 以及 CustomEditor 两处值，才能确认是哪一保存者覆盖。

## 残留风险

- 未覆盖区域：用户 ASE 版本、保存入口、是否还有外部脚本直接改写 `.shader`，以及项目中实际的 `CustomEditor` 值。
- 为何还不能安心发布：当前至少存在一个已验证的公开 `recompile` 丢失路径，且手工保存场景没有保护机制；在补上真相源与实机再保存回归前，不应承诺“自定义 GUI 可稳定持久化”。
