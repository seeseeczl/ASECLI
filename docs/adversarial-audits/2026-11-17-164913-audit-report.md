## 审计边界

- **范围**：本轮新增的两个编辑器桥，及承接它们的选择层
  - `src/asecli/bridge/bridge_client.py`（DSH-Bridge，文件邮箱 IPC）
  - `src/asecli/bridge/codely_client.py` / `codely_discovery.py` / `codely_probe.py`（Codely，TCP）
  - `src/asecli/bridge/backend.py`（三后端选择）
  - `src/asecli/bridge/editor_result.py`（统一解包）
  - 默认值变更：`--editor-backend` 默认 `auto`
- **邻域**：5 个调用点（`editor_create` / `graph_inspect` / `graph_geometry` / `recompile` / `wire_route`）、CLI 层、测试
- **方法**：只读代码审查 + 真机动态验证（真实编辑器 pid 70407、真实邮箱、真实 C# 执行）
- **威胁假设**：本机存在不可信进程；多工程/多编辑器并存；桥会升级；用户凭 CLI 输出判断操作结果
- **审计对象边界声明**：DSH-Bridge 探针与插件源码属外部组件，本轮仅就从 ASECLI 视角观察到的行为做评估，不修改它们

## 威胁与失败模型

- **资产**：ASE shader 资产正确性；CLI 结果可信度；本机文件读取面
- **攻击者能力**：本机任意进程可读写 `Library/DSHBridge/` 与工程文件；可伪造 `instance.json`；可向 `inbox` 投放恶意 JSON
- **最贵失败**：ASECLI 报告成功但实际未执行/执行到错误工程；或邮箱队列被毒消息阻塞导致所有命令超时

## Findings 详情

### [P1] AA-SEC-010 — `unity.code.execute` 默认开启且无沙箱 — `bridge_client.py:COMMAND_EXECUTE`
- **证据等级**：已验证
- **触发条件**：任一调用方（含 ASECLI）通过 `unity.code.execute` 执行任意 C#
- **错误行为**：该能力不在 `DEFAULT_DANGEROUS` 清单内，因此**无需任何授权**即可使用；脚本以编辑器进程权限运行
- **复现**：
  ```csharp
  return System.IO.File.ReadAllText("/etc/hosts").Length > 0 ? "file-read-ok" : "no";
  → {"ok": true, "result": "file-read-ok"}
  ```
- **影响**：桥设计的“危险能力白名单”（`reflect.invoke` / `api.invoke` / `api.batch` 等均需授权）对这条通道**形同虚设**。任何能写 `inbox` 的本机进程都能获得编辑器权限的任意代码执行。白名单只约束了“从哪扇门进”，而 `code.execute` 是一扇常开的门
- **补充事实**：`DEFAULT_DANGEROUS` 的注释确认这是**有意为之**（“ASECLI 的 ASE 编辑流程依赖它”），但该权衡未在 `instance.json`/文档中向调用方披露
- **最小修复方向**：在 ASECLI 侧把该能力的使用收敛到唯一的 `execute_code` 通道并在结果中标注；同时向 Bridge 提议把 `code.execute` 加入 `grantedCapabilities` 审计，或提供“仅允许注册脚本”的受限模式
- **关联优化任务**：AA-OPT-010

### [P1] AA-DATA-011 — 毒消息阻塞邮箱队列 — `bridge_client.py:execute_code`（与探针 `Poll()` 协同）
- **证据等级**：已验证
- **触发条件**：`inbox/` 中存在一个无法解析的 `*.json`（崩溃残留、磁盘半写、外部进程投放）
- **错误行为**：探针 `Poll()` 每次只取 `files[0]`；坏文件解析失败后虽被移走，但在它被处理前**排在后面的所有请求都被饿死**
- **复现**：
  ```
  写入 aaa_broken.json（截断 JSON）+ 一个正常请求
  正常请求被处理, polls=205   ← 明显排队等待
  ```
- **影响**：ASECLI 侧表现为“桥超时”，但根因是队列阻塞；且坏文件由**任何**能写 `inbox` 的进程引入，ASECLI 自身崩溃留下的 `.tmp` 也可能成为污染源
- **最小修复方向**：客户端写请求前做一次队列健康检查；Bridge 侧改为“跳过坏文件并记录”而非顺序阻塞（对外提议）
- **关联优化任务**：AA-OPT-011

### [P2] AA-LOGIC-012 — `auto` 每次调用重复探测 — `backend.py:run_editor_code`
- **证据等级**：已验证
- **触发条件**：`--editor-backend auto`（当前默认）且连续调用多次（如 `layout`）
- **错误行为**：`run_editor_code` 每次执行都调用 `select_backend`，后者依次 `bridge_probe` → `codely_probe` → `probe_mcp`；三者默认超时各 30s
- **复现**：`bridge_probe` / `codely_probe` 签名默认 `timeout=30.0`；全失败路径最长约 90s，且下一条命令再付一次
- **影响**：桥全部不可用时，用户体验是“每条命令卡 1.5 分钟”，而非快速失败
- **最小修复方向**：进程内缓存选择结果（带短 TTL），或在全失败时快速返回并提示
- **关联优化任务**：AA-OPT-012

### [P2] AA-DATA-013 — 模块文档与实现不一致 — `bridge_client.py:1-6`
- **证据等级**：已验证
- **触发条件**：维护者依据 docstring 实现/排障
- **错误行为**：docstring 写 “the answer appears in ``done/``”，而实现读 `outbox/`（`_read_response`）
- **复现**：`grep -n "done" bridge_client.py` → 第 5 行；`grep -n outbox` → 第 117/139/149/181 行
- **影响**：这是本轮开发中**实际踩过的坑**（按 `done/` 读会拿到请求回显）。文档不修，下一个人会重踩
- **最小修复方向**：改正 docstring，并说明 `done/` 存放的是被处理过的请求
- **关联优化任务**：AA-OPT-013

### [P2] AA-DATA-014 — 超时后请求仍被执行 — `bridge_client.py:execute_code` finally 分支
- **证据等级**：已验证
- **触发条件**：客户端超时（`timeout`）但探针仍在处理该请求
- **错误行为**：`finally` 删除 inbox 里的请求文件；探针已把请求移入 `in-progress` 并继续执行，完成后写 `outbox` 并移入 `done`
- **复现**：`done/` 中出现 `req_asecli_*` 残留（本轮观察到 4 个）
- **影响**：ASECLI 报告“超时失败”，但**副作用可能已发生**（例如建图已写入资产）。调用方若重试会产生重复操作
- **最小修复方向**：结果中区分“未投递 / 已投递但超时”；超时后提示先检查目标状态（Bridge 已有类似措辞）
- **关联优化任务**：AA-OPT-014

### [P3] AA-LOGIC-015 — 邮箱协议无幂等保护 — `bridge_client.py:execute_code`
- **证据等级**：已验证
- **触发条件**：两个请求使用相同 `id`
- **错误行为**：后写入者覆盖前者，探针只执行一份
- **复现**：同 id 连写两次 → 响应只有 `"second"`
- **影响**：ASECLI 用 UUID 生成 id，实际不撞号；但协议层无保护，若将来复用 id 或做重试会静默丢失请求
- **最小修复方向**：ASECLI 侧保持 UUID；协议层建议探针检测重复 id
- **关联优化任务**：AA-OPT-015

## DSH-Bridge 的欠缺（对外组件评估）

本轮实测确认**能力面已满足 ASECLI**，以下为“还缺什么”的结论：

| 项 | 现状 | 对 ASECLI 的影响 |
| --- | --- | --- |
| `unity.code.execute` | ✅ 默认开启，可用 | 核心依赖，够用 |
| `unity.api.batch` | ⚠️ 默认关闭 | **不需要**：建图事务在单脚本 try/finally 内完成 |
| `unity.asset.refresh` | ⚠️ 默认关闭 | **不需要**：`AssetDatabase.ImportAsset` 经 `code.execute` 实测可用 |
| 嵌套对象返回 | ✅ 支持 | 够用 |
| `resultTruncated` | ✅ 有显式标记 | 够用（客户端已强制拒绝） |
| 发现协议 | ✅ `discoveryVersion`/`staleAfterMs`/`sourceHash` | 够用 |
| 队列健壮性 | ❌ 毒消息阻塞 | **建议补**（见 AA-DATA-011） |
| 执行超时语义 | ⚠️ 有提示但无机器可读标记 | **建议补**：区分“未执行/可能已执行” |
| 幂等 | ❌ 无 | 建议补 |

**结论**：Bridge 侧不必为本轮再扩能力；建议优先补**队列健壮性**与**执行结果状态标记**两项。

## 测试与观测缺口

- **缺失用例**：毒消息阻塞、超时后副作用残留、同 id 覆盖、`auto` 探测耗时的缓存行为
- **缺失观测**：未记录实际使用的能力名与请求 id 到 CLI 输出，排障需手工翻邮箱

## 残留风险

- **未覆盖区域**：多编辑器同工程并发写同一邮箱未实测；Bridge 升级后协议漂移无自动检测（仅靠 `probeVersion`/`sourceHash` 展示）
- **为何还不能安心发布**：AA-SEC-010 是**设计性权衡**（非实现 bug），但它改变了对“桥 = 安全边界”的理解，需使用者知情

## 总评

- **结论**：**条件通过**
- **前置条件**：
  1. AA-OPT-010：在文档与 CLI 输出中明确 `code.execute` 的权限等级
  2. AA-OPT-011：加队列健康检查或快速失败
  3. AA-OPT-012：避免每次调用重复探测
