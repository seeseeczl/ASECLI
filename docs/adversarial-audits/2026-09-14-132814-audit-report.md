## 威胁与失败模型

- 资产：独立 CLI 运行、可重复发布、JSON 兼容性、仓库写入边界。
- 对方仓库可能暂不可访问、存在未提交改动、接口加性升级或主分支变化。
- 任一方应能离线验证本地固定协议，而不要求安装/获取对方实现。
- 不支持的语义必须拒绝并生成诊断，不通过跨仓自动修复或弱化验证掩盖。
- 最贵失败：自身代码无变化却无法发布；为解锁发布误改对方；混装测试漏掉真实运行依赖。

## Findings 详情

### [P1] AA-COUP-001 — 将跨仓检查从单仓必需发布路径分离

- 证据：ASECLI `.github/workflows/publish.yml:103-104` 的 publish 需要 `[package, cross-cli]`；cross-cli 从对方仓库取得代码、构建 wheel、执行 SGCLI/scripts 内的校验实现，并要求对方 commit 与 SSH secret。ASECLI `.github/workflows/ci.yml:97` 默认接入相同检查。
- SGCLI `.github/workflows/ci.yml:103-108` 在 main / tag CI 接入跨仓检查，使用 ASECLI 浮动 `main`；`.github/workflows/cross-cli.yml:36-38` checkout 对方。这里只证明 SGCLI 默认 CI 被绑定，未发现同等的 SGCLI PyPI publish job，不扩大为该发布机制已验证。
- 触发：对方仓库/权限不可用，或对方 main 变化导致矩阵不通过。
- 影响：ASECLI 正式发布被阻断；SGCLI 同一提交的 CI 可受对方 main 影响，违反独立维护要求。
- 两仓 `tests/test_cross_cli_workflow.py` 还强制检查这种关联存在；ASECLI 测试第 18 行直接要求 publish 的跨仓 needs。仅删 workflow 引用会导致本地测试失败，需在本仓同时更新对应测试。
- 修复方向：单仓发布依赖自身检查、固定协议夹具和独立 wheel smoke；可选跨产品黑盒测试移出单仓必需发布路径，最好独立测试工程管理。分别在每个仓库执行，不自动联动。
- 关联：AA-OPT-001。

### [P1] AA-COUP-002 — 区分协议快照完整性与跨版本兼容性

- 证据：SGCLI `scripts/cross_cli_wheels.py:74-105` 读取两包四份 Schema 并直接比较 `consumer_raw == producer_raw`；`scripts/check_cross_cli_contracts.py:370-398` 将相等性纳入 ok。两仓 README 明确要求同步双方候选快照。
- 触发：对方只改 Schema 排版、说明或添加兼容字段，生产者仍产生被目标支持的 JSON，但字节摘要不同。
- 影响：语义兼容也要求同步更新/发布；Schema 名称保持 v3 时又增添新能力，会进一步造成版本标签不能充分表达能力集合。
- 修复方向：本包固定 Schema 的自完整性 SHA 校验保留；不要要求始终等于对方当前分支。以明确协议修订/能力集合和正负 JSON 夹具验证支持范围。新能力不能因单方发布就声明所有旧消费者可用。
- 注意：随包携带静态 JSON Schema 是允许的协议关联，不是运行代码依赖，不应删除。
- 关联：AA-OPT-002。

### [P2] AA-COUP-003 — 集成工具仍读取另一仓库内部结构

- 证据：SGCLI `scripts/check_cross_cli_contracts.py:52` 读取兄弟仓库源码 Schema；第 344 行默认 `../ASECLI`，第 370-377、425-428 行依赖双方仓库身份和干净工作树；`scripts/e2e_sgcli_to_ase.py:34` 默认使用 `../ASECLI/.venv/bin/asecli`。
- 触发：只克隆一个仓库、另一个仓库目录不同，或另一个任务有未提交布局改动。
- 影响：集成验证依赖对方开发目录，不符合“工具仓库之间不保留实现关联”的强独立目标。当前脚本以读取/执行为主，未据此认定会自动编辑另一仓源码。
- 修复方向：两个工具仓库各保留自身协议测试；跨产品场景搬到单独、显式运行的黑盒测试工程，只接受已发布包/可执行文件和 JSON，不读取对方 src 或 git 状态。不要为通过测试自动 stash/commit 对方。
- 关联：AA-OPT-003。

### [P2] AA-COUP-004 — 增加仅安装自身的运行独立性反例

- 证据：SGCLI `scripts/cross_cli_wheels.py:46-67` 把两个 wheel 安装到同一个 venv；这类测试即使通过，也不能排除未来代码隐式使用对方包。
- 边界：两仓现有 package job 已有单 wheel smoke，这是有效局部证据；缺口在完整的独立导出/校验/失败路径与跨仓调用禁止验证，不是“完全没有独立测试”。
- 触发：后续新增对方 import、PATH 子进程调用或开发目录读取，但混装测试依然通过。
- 修复方向：分别在只安装自身 wheel、无兄弟目录、对方不在 PATH 的隔离环境验证本工具导出与 JSON 校验；加静态禁止互相 import/路径引用检查。验证非法或不支持 JSON 仍失败关闭。
- 关联：AA-OPT-004。

## 当前没有发现的运行代码耦合

- 两边 `pyproject.toml` 的运行 `dependencies=[]`，wheel 配置只打包自身代码与自身携带的静态数据。
- 检查两边 src Python，未发现互相 import、子进程启动对方 CLI、动态导入对方或对方开发目录路径引用。
- 两边 contracts.py 从各自包资源加载 Schema，`package`/`version` 字符串是元数据，不是安装依赖。未发现互相链接的 tracked symlink/submodule。
- ASECLI 生成 JSON，SGCLI 自己读取并验证；转换报告规则分别实现。相似规则/重复校验不等于共享可执行模块。
- SGCLI 资源证据重查需要 JSON 所指向的源/目标图片和 meta 可访问，这是资源可移植性限制，不是必须安装 ASECLI。不得为了独立性直接删除证据校验。
- MultiplySourceAlpha 还依赖目标工程的对应 URP 能力，这是引擎能力依赖，不是 CLI 互相依赖。
